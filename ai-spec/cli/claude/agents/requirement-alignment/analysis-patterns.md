# 需求分析模式库 (Analysis Patterns)

> 常见的需求问题模式及识别方法

## 歧义模式 (Ambiguity Patterns)

### 1. 模糊动词
**特征**: 使用不精确的动词描述功能

| 模糊表达 | 需要澄清 |
|----------|----------|
| "处理数据" | 是验证、转换、存储还是分析？ |
| "管理用户" | 是 CRUD、权限控制还是用户行为管理？ |
| "优化性能" | 优化什么指标？目标值是多少？ |
| "支持XX" | 是完全支持还是部分支持？支持到什么程度？ |

### 2. 隐含主体
**特征**: 未明确说明动作的执行者或对象

```
❌ "需要发送通知"
   → 谁发送？发送给谁？什么时候发送？

✅ "当订单状态变更时，系统自动向下单用户发送邮件通知"
```

### 3. 量化缺失
**特征**: 缺少具体的数量、时间、程度限定

```
❌ "系统需要快速响应"
   → 多快算快？1秒？100毫秒？

✅ "API 响应时间 P99 < 200ms"
```

### 4. 条件不完整
**特征**: if-then 结构不完整，缺少边界条件

```
❌ "用户可以上传文件"
   → 什么格式？多大？多少个？

✅ "用户可以上传 JPG/PNG 格式图片，单个文件 ≤ 5MB，每次最多 10 个"
```

## 缺失模式 (Missing Patterns)

### 1. 错误路径缺失
常见缺失场景:
- 网络断开时怎么办？
- 数据格式错误如何处理？
- 权限不足时的反馈？
- 并发冲突如何解决？

### 2. 边界条件缺失
需要考虑:
- 空值/null 情况
- 极大/极小值
- 首次使用/初始状态
- 数据迁移/历史兼容

### 3. 非功能需求缺失
经常被忽略:
- 性能要求 (响应时间、吞吐量)
- 安全要求 (认证、授权、加密)
- 可用性要求 (容错、恢复)
- 可观测性 (日志、监控、告警)

### 4. 用户体验缺失
需要明确:
- 加载状态显示
- 操作反馈
- 撤销/重做能力
- 快捷键/批量操作

## 冲突模式 (Conflict Patterns)

### 1. 需求内部冲突
```
需求: "系统要简单易用，同时提供丰富的配置选项"
冲突: 简单性 vs 灵活性
解决: 分层设计 - 默认简单，高级选项可选
```

### 2. 与现有系统冲突
检查点:
- 数据格式是否兼容？
- API 契约是否一致？
- 业务规则是否冲突？
- 用户体验是否统一？

### 3. 资源约束冲突
```
需求: "支持实时同步，同时离线可用"
冲突: 实时性 vs 离线能力
解决: 明确优先级，设计冲突解决策略
```

## 风险模式 (Risk Patterns)

### 1. 技术风险
- 使用不熟悉的技术栈
- 依赖不稳定的第三方服务
- 性能要求超出当前架构能力
- 安全要求超出团队经验

### 2. 业务风险
- 需求来源单一，可能不代表真实用户
- 市场变化可能导致需求失效
- 法规合规要求可能变化

### 3. 资源风险
- 时间估算过于乐观
- 依赖不确定的外部资源
- 关键人员可能不可用

## 问题发现检查清单

### 快速检查 (每个需求必做)
- [ ] 有没有使用模糊动词？
- [ ] 主体和对象是否明确？
- [ ] 有没有量化指标？
- [ ] 错误场景考虑了吗？

### 深度检查 (复杂需求)
- [ ] 画出用户旅程，每个步骤是否明确？
- [ ] 列出所有状态，状态转换条件是否清晰？
- [ ] 识别所有角色，权限边界是否清晰？
- [ ] 检查与现有功能的关系，是否有冲突？

### 验收检查 (对齐完成前)
- [ ] 能否根据需求写出测试用例？
- [ ] 开发人员阅读后有疑问吗？
- [ ] 估算工作量时有不确定性吗？
- [ ] 用户能理解并确认这是他们想要的吗？
