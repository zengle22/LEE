# 产品目标价值分析能力

这是一个可复用的分析能力模块，提供完整的产品需求价值分析框架，并生成Contract文档。

## 能力概述

将产品需求转化为结构化的价值分析，输出Contract文档，确保业务价值穿达清晰。

**输入**：产品需求描述
**输出**：Contract文档（关键设计需人类确认）

---

## Contract概念

### 什么是Contract

Contract（契约文档）不同于普通的分析报告：

| 普通报告 | Contract |
|----------|----------|
| 信息展示 | 交付约定 |
| 可选阅读 | 必须确认 |
| 单向输出 | 双向确认 |
| 一次生成 | 状态流转 |

### Contract状态

```
📝 DRAFT                    Agent生成草稿
    ↓
🔍 PENDING_CONFIRMATION     等待人类确认关键设计
    ↓
✅ CONFIRMED                全部关键设计已确认
    ↓
🎯 APPROVED                 最终审批通过，Contract生效
```

### 关键设计确认点

Contract中有4个关键设计点，**每个都需要人类显式确认**：

| # | 确认点 | 确认内容 |
|---|--------|----------|
| 1 | 核心目标 | 目标定义、衡量指标、成功标准 |
| 2 | 价值穿达链 | 价值传导路径、逻辑一致性 |
| 3 | 优先级判定 | 评分依据、优先级、资源预估 |
| 4 | 风险与边界 | 风险识别、边界定义、依赖关系 |

## 分析框架

### 第一步：信息提取

从需求中提取关键信息：

| 字段 | 必填 | 说明 |
|------|------|------|
| 需求标题 | ✅ | 简洁的需求名称 |
| 需求描述 | ✅ | 详细说明 |
| 目标用户 | ✅ | 服务的用户群体 |
| 提交人 | ✅ | 需求来源 |
| 期望时间 | ❌ | 预期上线时间 |
| 补充上下文 | ❌ | 背景信息 |

---

### 第二步：四维度分析

#### 维度一：用户价值 👥

**分析要点**：
1. 解决什么用户痛点？痛点有多强烈？
2. 用户能获得什么具体收益？
3. 影响的用户规模有多大？
4. 是否改变用户习惯？接受度如何？

**评分标准**：

| 评分 | 标准 |
|------|------|
| 🟢 HIGH | 痛点明确且强烈、收益显著可量化、影响大规模用户(>50%) |
| 🟡 MEDIUM | 痛点存在但不紧迫、收益一般、影响部分用户(10-50%) |
| 🔴 LOW | 痛点不清晰、收益难描述、影响少量用户(<10%) |

#### 维度二：行业情况 📊

**分析要点**：
1. 是否符合行业发展趋势？
2. 竞品是否已有类似功能？差异化在哪？
3. 是否存在行业壁垒或合规要求？
4. 市场机会有多大？

**评分标准**：

| 评分 | 标准 |
|------|------|
| 🟢 HIGH | 顺应趋势、有差异化优势、机会明确 |
| 🟡 MEDIUM | 趋势中性、与竞品相当、机会待验证 |
| 🔴 LOW | 逆势而行、缺乏差异化、机会不明 |

#### 维度三：生产效率 ⚙️

**分析要点**：
1. 对团队效率有什么影响？
2. 是否有自动化的潜力？
3. 技术复杂度如何？实现周期预估？
4. 是否可以复用已有能力？

**评分标准**：

| 评分 | 标准 |
|------|------|
| 🟢 HIGH | 显著提升效率、高自动化潜力、可复用 |
| 🟡 MEDIUM | 效率影响中性、部分自动化、标准开发 |
| 🔴 LOW | 可能降低效率、复杂度高、周期长 |

#### 维度四：成本管理 💰

**分析要点**：
1. 开发成本预估（人力、时间）？
2. 运营成本预估（云资源、第三方服务）？
3. 投资回报预期（ROI）如何？
4. 有哪些成本节约的机会？

**评分标准**：

| 评分 | 标准 |
|------|------|
| 🟢 HIGH | 成本可控、ROI明确为正、有节约机会 |
| 🟡 MEDIUM | 成本中等、ROI待验证 |
| 🔴 LOW | 成本高昂、ROI不明或为负 |

---

### 第三步：关键设计提取

#### 关键设计1: 核心目标

**主要目标 (PRIMARY)**
- 需求最核心要解决的问题
- 必须有可衡量的指标
- 必须有明确的成功标准
- 说明为什么这个目标重要

**次要目标 (SECONDARY)**
- 需求附带带来的价值
- 同样需要可衡量的指标

```yaml
core_goals:
  primary:
    description: "目标描述"
    rationale: "为什么重要"
    metrics: ["指标1", "指标2"]
    success_criteria: ["标准1", "标准2"]
  secondary:
    - description: "次要目标1"
      metrics: ["指标"]
```

#### 关键设计2: 业务价值穿达链

建立完整的价值传导链路：

```
用户需求 → 产品功能 → 直接价值 → 业务影响 → 战略意义
```

每个环节需要：
- 明确描述
- 验证方式

| 环节 | 问题 | 验证方式 |
|------|------|----------|
| 用户需求 | 用户遇到什么问题？ | 用户调研/反馈 |
| 产品功能 | 我们做什么来解决？ | 功能验收 |
| 直接价值 | 用户直接获得什么？ | 用户体验测试 |
| 业务影响 | 对业务有什么影响？ | 业务指标监控 |
| 战略意义 | 对公司战略有何意义？ | 战略Review |

#### 关键设计3: 优先级与资源

**综合评分计算**：
```
综合评分 = 用户价值×0.35 + 行业情况×0.20 + 生产效率×0.20 + 成本管理×0.25
```

**优先级判定**：

| 综合评分 | 用户价值 | 优先级 |
|----------|----------|--------|
| HIGH | HIGH | **P0** - 最高优先级 |
| HIGH | MEDIUM | **P1** - 高优先级 |
| MEDIUM | HIGH | **P1** - 高优先级 |
| MEDIUM | MEDIUM | **P2** - 中优先级 |
| LOW | 任意 | **P3** - 低优先级 |

#### 关键设计4: 风险与边界

**风险识别**：
- 用户风险
- 技术风险
- 市场风险
- 成本风险
- 时间风险

**边界定义**：
- IN SCOPE: 本需求包含
- OUT OF SCOPE: 本需求不包含

**依赖关系**：
- 前置依赖
- 并行依赖

## Contract文档生成

使用 `templates/product-goal-contract.md` 模板生成Contract文档。

### 文档结构

```
# 产品目标价值Contract

## Contract基本信息

## 需求概述

# ⚠️ 关键设计确认区

## 关键设计1: 核心目标定义
  ✋ 确认点 #1

## 关键设计2: 业务价值穿达链
  ✋ 确认点 #2

## 关键设计3: 优先级与资源投入
  ✋ 确认点 #3

## 关键设计4: 风险与边界
  ✋ 确认点 #4

# 详细分析（参考信息）

# Contract确认与审批
```

## 人类确认流程

### 确认交互模式

生成Contract后，需要逐一引导人类确认每个关键设计：

```
🎯 确认点 1/4: 核心目标定义

[展示核心目标内容]

请确认：
□ 目标是否准确描述了最核心问题？
□ 衡量指标是否可量化？
□ 成功标准是否明确？

回复"确认"继续，或提供修改意见。
```

### 确认记录

每个确认点需要记录：
- 确认状态：待确认 / 已确认 / 需修改
- 确认人
- 确认时间
- 人类反馈（如有）

### 修改处理

如果人类提供修改意见：
1. 更新Contract相关内容
2. 重新展示修改后的内容
3. 再次请求确认
