# 测试类型定义 v1.1
# Test Types Definition

## 概述

本文档定义测试流水线中各测试类型的概念、职责边界和适用场景。
所有测试 Agent 和 Skill 必须遵循这些定义。

## 2. 冒烟测试 (Smoke Test)

### 2.1 定义

```yaml
smoke_test:
  definition: >
    冒烟测试是最基本的健康检查，验证系统核心功能是否可用。
    名称来源于硬件测试：通电后如果冒烟，说明有严重问题。

  purpose: "快速判断版本是否值得进一步测试"

  analogy: "检查车能不能发动，不是检查每个功能是否正常"
```

### 2.2 特征

| 特征 | 描述 |
|------|------|
| **用例数量** | 5-10 条 |
| **执行时间** | < 10 分钟 |
| **覆盖范围** | 核心接口/页面可访问 |
| **执行方式** | 全自动 (API/脚本) |
| **失败后果** | 直接打回，不进入后续测试 |

### 2.3 典型用例

```yaml
smoke_test_examples:
  - "首页能否正常加载"
  - "登录接口是否返回 200"
  - "核心 API 是否可达"
  - "数据库连接是否正常"
  - "缓存服务是否可用"
```

### 2.4 不适合冒烟的场景

```yaml
not_for_smoke:
  - "边界条件验证"
  - "复杂业务流程"
  - "异常处理逻辑"
  - "性能相关测试"
```

## 3. E2E 测试 (End-to-End Test)

### 3.1 定义

```yaml
e2e_test:
  definition: >
    E2E 测试模拟真实用户在真实环境中的完整操作流程。
    使用真实浏览器或小程序沙箱，执行点击、输入、导航等操作。
    验证从用户视角看，核心功能是否可用。

    ⚠️ 关键约束：E2E 测试禁止任何形式的代码 Mock！

  purpose: "验证用户能否完成关键任务"

  analogy: "让一个人坐进车里，从A点开到B点，验证整个驾驶体验"

  strict_requirements:
    禁止项:
      - "❌ 禁止 mock 后端 API 响应"
      - "❌ 禁止 mock 数据库查询"
      - "❌ 禁止 mock 第三方服务"
      - "❌ 禁止注入假数据绕过真实流程"

    必须项:
      - "✅ 必须使用运行中的真实前端服务"
      - "✅ 必须使用运行中的真实后端服务"
      - "✅ 必须连接真实的数据库"
      - "✅ 所有网络请求必须通过真实 HTTP 调用"

    允许的"准备数据":
      - "✅ 可以预先准备测试账号"
      - "✅ 可以预先准备测试数据（通过真实 API 创建）"
      - "✅ 可以清理测试后的数据"
```

### 3.2 特征

| 特征 | 描述 |
|------|------|
| **用例数量** | 20-50 条 (核心场景) |
| **执行时间** | 30-120 分钟 |
| **覆盖范围** | 核心用户旅程 (User Journey) |
| **执行方式** | 全自动 (Playwright/小程序自动化) |
| **执行环境** | 真实浏览器 + 真实前后端服务 |
| **Mock 策略** | ❌ **禁止任何代码 Mock** |
| **失败后果** | 进入 Bug 修复循环 |

### 3.3 E2E 测试架构

```
┌─────────────────────────────────────────────────────────────────┐
│                    E2E 测试真实环境                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌─────────────┐     ┌─────────────┐     ┌─────────────┐      │
│  │  真实浏览器  │ ──→ │ 真实前端服务 │ ──→ │ 真实后端服务 │      │
│  │ (Playwright) │     │  (localhost │     │ (localhost  │      │
│  │             │     │    :3002)   │     │    :8081)   │      │
│  └─────────────┘     └─────────────┘     └──────┬──────┘      │
│                                                     │            │
│                                            真实网络请求 │            │
│                                                     ↓            │
│                                          ┌──────────────┐        │
│                                          │ 真实数据库    │        │
│                                          │ (PostgreSQL  │        │
│                                          │  + Redis)    │        │
│                                          └──────────────┘        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘

❌ 错误做法 (Mock 后端):
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  真实浏览器  │ ──→ │ 真实前端服务 │ ──→ │ Mock 响应    │ ← 禁止！
│  (Playwright)│     │  (localhost  │     │ (page.route)│
│             │     │    :3002)    │     │             │
└─────────────┘     └─────────────┘     └─────────────┘
```

### 3.4 为什么禁止 Mock？

```yaml
no_mock_rationale:
  真实性:
    - "用户使用时不会有人帮忙 mock API"
    - "真实网络延迟、错误响应只有在真实调用中才能发现"
    - "集成问题（如 CORS、序列化）只有真实环境才能暴露"

  完整性:
    - "前端 → 后端 → 数据库 的完整链路必须验证"
    - "事务回滚、并发冲突只有真实数据库能测试"
    - "缓存一致性只有真实缓存能验证"

  可信度:
    - "Mock 测试通过 ≠ 真实环境可用"
    - "Mock 可能掩盖真实的集成问题"
    - "E2E 的价值就是验证真实集成，Mock 会抵消这个价值"
```

### 3.5 E2E vs 集成测试 (区分关键)

```yaml
e2e_vs_integration:
  E2E测试:
    环境: "真实前端 + 真实后端 + 真实数据库"
    Mock: "❌ 禁止任何 Mock"
    验证: "用户能否完成真实操作"

  集成测试:
    环境: "可以部分 Mock（如 mock 外部支付 API）"
    Mock: "✅ 允许 Mock 非被测依赖"
    验证: "模块间接口是否正确"

  区分标准:
    question: "是否使用了 page.route() 或类似 mock？"
    if_yes: "这是集成测试，不是 E2E 测试"
    if_no: "这是真正的 E2E 测试"
```

### 3.6 E2E 关注点

```yaml
e2e_focus:
  关注:
    - "用户能否完成核心流程"
    - "页面是否正确渲染"
    - "交互是否符合预期"
    - "跨页面数据是否正确传递"
    - "真实环境下的集成问题"

  不关注:
    - "所有边界条件"
    - "所有错误处理分支"
    - "性能指标"
    - "安全漏洞"
```

### 3.7 典型用例

```yaml
e2e_test_examples:
  电商场景:
    - "用户注册 → 登录 → 浏览商品 → 加购 → 下单 → 支付"
    - "用户登录 → 查看订单 → 申请退款"
    - "用户搜索商品 → 筛选 → 对比 → 收藏"

  SaaS场景:
    - "管理员登录 → 创建项目 → 邀请成员 → 分配权限"
    - "用户登录 → 创建文档 → 编辑 → 分享 → 协作"
```

### 3.8 E2E vs UI 测试

```yaml
e2e_vs_ui:
  E2E测试:
    focus: "完整用户流程"
    scope: "跨多个页面/组件"
    verification: "业务流程能否走通"

  UI测试:
    focus: "单个组件/页面"
    scope: "组件级别"
    verification: "UI 是否正确渲染"

  relationship: "E2E 包含 UI 交互，但目标是验证流程而非 UI 本身"
```

## 4. 系统测试 (System Test)

### 4.1 定义

```yaml
system_test:
  definition: >
    系统测试是对完整系统的全面功能验证。
    覆盖所有功能模块、业务规则、边界条件和异常处理。
    可以是自动化测试，也可以是手工测试。

  purpose: "验证系统功能是否完整正确"

  analogy: "检查车的每个功能：空调、音响、安全带、后视镜、雨刷..."
```

### 4.2 特征

| 特征 | 描述 |
|------|------|
| **用例数量** | 100-500+ 条 |
| **执行时间** | 4-8 小时 |
| **覆盖范围** | 全功能、全模块 |
| **执行方式** | 自动化 + 手工混合 |
| **执行环境** | 测试环境 (可以是 API 级) |
| **失败后果** | 创建 Bug，进入修复循环 |

### 4.3 系统测试关注点

```yaml
system_test_focus:
  功能测试:
    - "每个功能是否按需求工作"
    - "输入输出是否正确"
    - "业务规则是否正确执行"

  边界测试:
    - "最大值/最小值处理"
    - "空值/null 处理"
    - "特殊字符处理"

  异常测试:
    - "错误输入的处理"
    - "网络异常的处理"
    - "并发冲突的处理"

  集成测试:
    - "模块间接口是否正确"
    - "数据流转是否完整"
    - "第三方集成是否正常"
```

### 4.4 典型用例

```yaml
system_test_examples:
  订单模块:
    正向:
      - "创建普通订单"
      - "创建带优惠券订单"
      - "创建跨境订单"
    边界:
      - "订单金额为 0.01"
      - "订单金额为 999999.99"
      - "商品数量为 1"
      - "商品数量为 99"
    异常:
      - "库存不足时下单"
      - "优惠券过期时使用"
      - "支付超时处理"
      - "重复提交订单"
```

## 5. E2E 与系统测试的关系

### 5.1 核心区别

```yaml
key_differences:
  视角:
    E2E: "用户视角 - 我能不能完成这个任务？"
    系统: "功能视角 - 这个功能是否正确？"

  范围:
    E2E: "少量核心流程，深度验证"
    系统: "全部功能，广度覆盖"

  环境:
    E2E: "必须是真实浏览器/客户端"
    系统: "可以是 API 级、脚本级"

  成本:
    E2E: "高 (浏览器启动、截图、录像)"
    系统: "相对低 (可以并行、可以 mock)"

  稳定性:
    E2E: "较脆弱 (依赖 UI 结构、网络)"
    系统: "较稳定 (接口契约明确)"
```

### 5.2 为什么需要两者？

```yaml
why_both_needed:
  scenario: "用户下单功能"

  only_e2e_problem: >
    如果只做 E2E：
    - 可能漏掉"库存不足时的处理"（E2E 不会刻意制造库存不足）
    - 可能漏掉"订单金额精度问题"（E2E 只验证能下单成功）
    - 可能漏掉"并发下单问题"（E2E 是单用户操作）

  only_system_problem: >
    如果只做系统测试：
    - 可能发现不了"结算按钮被遮挡"（系统测试不点按钮）
    - 可能发现不了"页面跳转丢失数据"（系统测试不经过前端）
    - 可能发现不了"移动端布局错乱"（系统测试不用真实浏览器）

  together: >
    E2E 保证"用户能走通"
    系统测试保证"每个细节都对"
```

### 5.3 执行顺序

```yaml
execution_order:
  sequence: "冒烟 → E2E → 系统"

  rationale:
    冒烟先行: "如果服务都起不来，后续测试没意义"
    E2E次之: "如果用户连登录都不行，测边界条件没意义"
    系统最后: "确认基本可用后，再深入验证细节"

  gate_logic:
    冒烟失败: "直接打回，不浪费 E2E 资源"
    E2E失败: "进入 Bug 循环，不浪费系统测试资源"
    系统测试发现Bug: "正常流程，继续修复验证"
```

## 6. 回归测试 (Regression Test)

### 6.1 定义

```yaml
regression_test:
  definition: >
    回归测试验证缺陷修复是否有效，且修复没有引入新问题。
    基于风险分析选择用例，而非全量执行。

  purpose: "确认修复有效，且没有破坏其他功能"

  analogy: "修完刹车后，不仅要试刹车，还要试试油门还能不能用"
```

### 6.2 回归范围选择

```yaml
regression_scope:
  必须包含:
    - "缺陷相关的直接用例"
    - "缺陷所在模块的冒烟用例"
    - "与该模块有接口依赖的模块的用例"

  可选包含:
    - "历史高频出问题的用例"
    - "核心链路用例"

  策略:
    P0_bug: "回归范围大，包含核心链路"
    P1_bug: "回归范围中等，模块内 + 直接依赖"
    P2_bug: "回归范围小，仅直接相关用例"
```

## 7. 验收测试 (Acceptance Test)

### 7.1 定义

```yaml
acceptance_test:
  definition: >
    验收测试是最终确认系统满足业务需求的测试。
    通常由产品经理或业务代表执行，关注业务价值。

  purpose: "确认系统满足业务需求，可以上线"

  analogy: "买家验车，确认这是我要的车，可以签字提车"
```

---

## 8. 测试类型选择指南

```yaml
selection_guide:
  "我想快速验证版本能否用":
    answer: "冒烟测试"

  "我想验证用户核心流程":
    answer: "E2E 测试"

  "我想验证所有功能细节":
    answer: "系统测试"

  "我想验证 Bug 修复":
    answer: "回归测试"

  "我想确认可以上线":
    answer: "验收测试"
```

## 9. 测试金字塔

```yaml
test_pyramid:
  description: >
    测试应该呈金字塔形状：底层多、上层少。
    E2E 在金字塔顶端，数量少但价值高。

  structure: |

           /\
          /E2E\        <- 少量核心流程 (20-50)
         /──────\
        /  系统   \     <- 中量功能用例 (100-500)
       /──────────\
      /   单元/接口  \   <- 大量底层测试 (1000+)
     /────────────────\

  anti_pattern: |

         ──────────
        │   E2E    │   <- 倒金字塔：E2E 过多
         ──────────
            │ │
         ──────
        │系统 │
         ──────
           │
         ────
        │单元│         <- 底层测试不足
         ────

    问题：执行慢、维护成本高、稳定性差
```
