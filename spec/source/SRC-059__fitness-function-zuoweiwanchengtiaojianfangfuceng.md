# Fitness Function 作为完成条件防腐层

## 问题陈述

### 完成语义分散问题

当前 LEE 工作流中完成语义分散在：
- gate rules
- integration threshold 文档
- testset
- evidence pack 约束
- agent 提示与 reviewer 心智

这导致系统知道很多局部规则，但缺少统一的完成条件入口。

### 现有 Gates 主要消费结果而非生成结果

当前 gate 更适合做：
- 阻断、升级、审批、freeze/reject/revise 决策

但不适合直接承担：
- 扫描仓库规则文件
- 执行命令采样
- 聚合多维度完成条件
- 产出统一 `fitness_result`

### 证据存在但完成证明未统一

存在证据，不等于存在完成证明。系统可能出现：
- evidence 很多，但审阅者仍要自己拼接是否真的闭环
- 某些 hard gate 已失败，但未被统一归纳到"不能退出循环"
- 某些关键未验证项未进入统一审查对象

### 核心问题

**agent 容易把"代码写了""局部测试过了""报错没了"误读为"任务完成"**

## 目标用户

| 用户群体 | 需求 |
|---------|------|
| LEE 工作流中的 AI 执行器 (agent) | 需要明确的完成条件与执行入口，通过 fitness runner 提供统一入口 |
| Supervisor 审查者 | 需要可审计的完成证明，fitness_result 提供结构化输出 |
| Gate 审批者 | 需要可消费的判定输入，hard_gate_results 直接对接 |
| 工程治理团队 | 需要规则覆盖率与执行追踪，dimension_results 提供多维度视图 |

## 业务动因

### 核心价值主张

- **用户需求**: AI 执行者和审查者需要明确的完成信号，避免完成误判导致的返工和审查成本
- **产品特性**: Fitness Function 作为完成条件防腐层，负责把规则解释权从分散文本和人工经验中收回来交给统一执行器
- **直接价值**: 减少完成误判，降低审查成本，提升 AI 交付质量一致性
- **业务影响**: 提升 LEE 工作流整体治理水平，增强 AI 交付可信度，降低人工审查负担
- **战略意义**: 实现 LEE 的 schema-first 治理方向，将完成条件从人工经验转向机器可执行规则

### 核心业务目标

> 建立统一的完成条件执行层，将分散的完成语义收敛为仓库内可执行、可审计的 fitness_result 对象

**动因**: 当前 gate 侧重消费已有上下文做判定，verifier 聚焦单类验证，evidence 记录执行结果但不统一表达完成条件，AI 容易将局部通过误读为整体完成

## 关键约束

### 依赖关系

| 依赖项 | 状态 | 影响 |
|--------|------|------|
| 现有 gate 语义与审批边界 | 已存在 | 需确保 fitness_result 可被消费 |
| 现有 evidence pack 与证据引用约束 | 已存在 | 需支持 fitness_result 回挂 |
| 现有 verifier 与 completion checker | 已存在 | 需明确边界，避免重叠 |
| supervisor gate 机制 | 已存在 | 需保留独立关闭边界 |

### 治理约束

- Fitness 不替代 gate，而是成为 gate 的上游输入
- Fitness 不替代人工 approval
- Fitness 结果必须进入 evidence pack
- Supervisor 仍保留最终独立关闭边界
- `fitness_result = pass` 不直接等价为 workflow completion

## 范围边界

### 纳入范围 (In Scope)

- 完成条件的仓库内声明方式
- 多维度 fitness 规则的统一执行入口
- hard_gate 与 score/warn 规则分层
- `fitness_result` 的结构化输出
- fitness 与 gate、evidence pack、supervisor 的对接
- CLI/CI 的最小接入面

### 排除范围 (Out of Scope)

- 用 fitness 替代人工 approval
- 用 fitness 替代需求链测试体系全部能力
- 在本 ADR 中冻结最终数据库 schema
- 在本 ADR 中冻结最终 UI 控制台形态
- 一次性迁移全部历史 gate/verifier/testset

## 定位决策

LEE 对 Fitness 的正式定位：

```
repo rules
  -> fitness runner
  -> fitness_result
  -> evidence pack / gate / supervisor
  -> completion decision
```

因此：
- Fitness 不是新的审批系统
- Fitness 不是新的 evidence 系统
- Fitness 不是新的 review 角色
- **Fitness 是"完成条件执行层"**

它负责把规则解释权从分散文本和人工经验中收回来，交给统一执行器。

## 验收信号

当本 SRC 对应能力落地后，至少应满足以下信号：

1. agent 无法仅凭"局部测试通过"就宣布可完成
2. hard gate 条件存在统一仓库内真源
3. gate 能直接消费统一 `fitness_result`
4. evidence pack 能回挂 fitness 执行结果
5. supervisor 审查时不再需要手工拼接主要完成条件
