## Critical Issues (Immediate Action Required)

### 🔴 SEC-001: Unsafe YAML Loading

**Severity:** Critical
**Location:** `src/lee/orchestrator/core/project_config.py`

**Description:**
The codebase uses both `yaml.safe_load()` and `yaml.load()` in different places. The `yaml.load()` function is vulnerable to arbitrary code execution if malicious YAML files are processed.

**Impact:**
- Potential remote code execution vulnerability
- Supply chain attack risk
- Data breach risk

**Recommendation:**
```python
# Replace all instances of:
yaml.load(file)

# With:
yaml.safe_load(file)
```

**Files Affected:**
- `src/lee/orchestrator/core/project_config.py`
- `src/lee/orchestrator/core/template_manager.py`

---

### 🔴 SEC-002: Shell Injection Risk

**Severity:** Critical
**Location:** `src/lee/orchestrator/execution/executors.py`

**Description:**
The `ShellExecutor` class uses `asyncio.create_subprocess_shell()` which passes commands through the shell. If user input is not properly sanitized, this leads to shell injection vulnerabilities.

**Current Code:**
```python
process = await asyncio.create_subprocess_shell(
    command,
    stdout=asyncio.subprocess.PIPE,
    stderr=asyncio.subprocess.PIPE,
    cwd=working_dir,
)
```

**Impact:**
- Command injection vulnerability
- Potential system compromise
- Data exfiltration risk

**Recommendation:**
```python
# Use create_subprocess_exec with argument list:
process = await asyncio.create_subprocess_exec(
    *shlex.split(command),
    stdout=asyncio.subprocess.PIPE,
    stderr=asyncio.subprocess.PIPE,
    cwd=working_dir,
)
```

### 🔴 SEC-003: Path Traversal Vulnerability

**Severity:** Critical
**Location:** `src/lee/orchestrator/core/project_config.py`

**Description:**
The `resolve_path()` method in `ProjectConfig` may allow path traversal attacks (e.g., `../../../etc/passwd`) if paths are not properly validated.

**Impact:**
- Unauthorized file access
- Information disclosure
- Potential system compromise

**Recommendation:**
```python
def resolve_path(self, path: str, context_dir: Path = None) -> str:
    # Add validation to prevent path traversal
    resolved = Path(resolved).resolve()
    base = self.base_path.resolve()

    # Ensure resolved path is within base
    try:
        resolved.relative_to(base)
    except ValueError:
        raise ValueError(f"Path outside project directory: {path}")
```

## High Priority Issues

### 🟠 ARCH-001: Tight Coupling Between Components

**Severity:** High
**Location:** `src/lee/orchestrator/`

**Description:**
The Orchestrator, Executors, and StateMachine components are tightly coupled. Changes in one component often require cascading changes in others. The "Executor Constitution" in `executors.py` documents architectural rules that some executors violate.

**Impact:**
- Difficult to modify components independently
- Hard to test in isolation
- Increased regression risk

**Recommendation:**
1. Implement proper dependency injection
2. Define clear interfaces between components
3. Enforce the "Executor Constitution" through code review
4. Consider using a dependency injection framework

---

### 🟠 ARCH-002: God Object Pattern - ProjectConfig

**Severity:** High
**Location:** `src/lee/orchestrator/core/project_config.py`

**Description:**
The `ProjectConfig` class handles too many responsibilities:
- Repository management
- Path resolution
- Directory structure initialization
- Configuration validation
- Output path generation

The file is over 800 lines and contains multiple large functions.

**Impact:**
- Violates Single Responsibility Principle
- Difficult to test
- Hard to maintain and understand
- High cyclomatic complexity

**Recommendation:**
Split into focused classes:
```python
# Suggested structure:
class RepositoryRegistry:
    """Manages repository configuration"""

class PathResolver:
    """Handles path resolution and alias expansion"""

class DirectoryStructureManager:
    """Manages directory structure initialization"""

class ConfigValidator:
    """Validates configuration files"""
```

#### CODE-001: Inconsistent Error Handling

**Severity:** Medium

Different modules use different error handling patterns:
- Some raise exceptions
- Some return error codes
- Some silently ignore errors

**Example Locations:**
- `src/lee/orchestrator/execution/variable_resolver.py`
- `src/lee/orchestrator/execution/condition_engine.py`
- `src/lee/orchestrator/execution/state_machine_executor.py`

**Recommendation:**
Establish a standard error handling pattern:
```python
# Define custom exceptions
class LeeError(Exception):
    """Base exception for LEE framework"""
    pass

class ValidationError(LeeError):
    """Raised when input validation fails"""
    pass

class ResolutionError(LeeError):
    """Raised when variable/path resolution fails"""
    pass
```

#### CODE-008: Insufficient Logging

**Severity:** Medium

Many operations lack appropriate logging:
- Error conditions caught without logging
- State changes not logged
- Important operations silent

**Recommendation:**
Add structured logging:
```python
import logging

logger = logging.getLogger(__name__)

def resolve_reference(self, reference, context):
    logger.debug(f"Resolving reference: {reference}")
    try:
        value = self._resolve(reference, context)
        logger.info(f"Resolved {reference} successfully")
        return value
    except ValueError as e:
        logger.error(f"Failed to resolve {reference}: {e}")
        raise
```
