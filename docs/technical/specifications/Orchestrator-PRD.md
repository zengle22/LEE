## 1. 产品概述

### 1.1 产品名称

**Orchestrator** - 通用 AI 工作流编排器

### 1.2 产品定位

Orchestrator 是一个**强制执行工作流规范的编排系统**，通过状态机、门禁机制和产物验证，让 AI Agent 按照预定义流程执行任务，确保"人类在环"控制和完整审计追踪。

### 1.3 核心价值主张

| 问题 | 解决方案 | 价值 |
|------|----------|------|
| Agent 可能跳过步骤 | 状态机强制执行 | 确保流程完整 |
| 人工审批被忽略 | Gate 产物化 | 不可绕过的控制点 |
| 产物验证被遗漏 | Artifact Gate | 强制质量检查 |
| 执行日志不完整 | 自动事件记录 | 完整审计追踪 |

### 1.4 产品愿景

成为 AI Agent 执行的**通用工作流编排标准**，让任何组织都能可靠地使用 AI Agent 完成复杂任务。

## 2. 背景与问题

### 2.1 市场背景

**趋势**：
- AI Agent 能力越来越强
- 企业开始用 AI Agent 自动化业务流程
- 需要"人类在环"控制关键决策

**挑战**：
- Agent 执行过程不透明
- 难以强制执行流程规范
- 缺少审计追踪能力
- 人工控制点容易被绕过

### 2.2 用户痛点

#### 痛点 1: Agent 自主性带来的不确定性

**现状**：
- Agent 可能跳过某些步骤
- Agent 可能忽略安全检查
- 难以预测 Agent 行为

**影响**：
- 流程不可控
- 质量风险
- 合规风险

#### 痛点 2: 人工审批流于形式

**现状**：
- Agent 可以直接提交，绕过审批
- 审批记录不完整
- 难以追溯责任

**影响**：
- 质量把关失效
- 责任不清
- 审计困难

#### 痛点 3: 产物验证依赖 Agent 自觉

**现状**：
- Agent 可能"忘记"验证
- 验证规则不统一
- 缺少验证记录

**影响**：
- 质量问题
- 返工成本高
- 客户投诉

#### 痛点 4: 执行日志不完整

**现状**：
- 日志依赖 Agent 主动记录
- 关键操作可能遗漏
- 难以回溯问题

**影响**：
- 问题定位困难
- 改进无依据
- 责任不清

### 2.3 现有解决方案分析

#### 方案 1: 完全手动流程

**优点**：
- 完全可控
- 灵活性高

**缺点**：
- 效率低
- 易出错
- 难以规模化

#### 方案 2: Agent 完全自主

**优点**：
- 效率高
- 无需人工干预

**缺点**：
- 不可控
- 风险高
- 缺少审计

#### 方案 3: 简单的工作流引擎

**优点**：
- 提供基本编排能力

**缺点**：
- 缺少强制执行机制
- 缺少人类在环控制
- 缺少完整审计

**结论**：需要一个新的解决方案，结合 Agent 自主性和人工控制。

### 3.2 用户场景

#### 场景 1: 软件开发流程

**角色**：开发团队
**流程**：
```
设计 → 代码实现 → 测试 → Code Review → 部署
  ↓       ↓        ↓        ↓          ↓
审批    自动     自动     审批       审批
```

**需求**：
- 强制执行每个步骤
- 设计、审查、部署必须人工审批
- 完整记录谁在何时做了什么

#### 场景 2: Bug 修复循环

**角色**：测试团队
**流程**：
```
发现 Bug → 报告 Bug → 等待修复 → 验证修复
  ↑                                      ↓
  └─────────────── 审批未通过 ────────────┘
```

**需求**：
- 支持循环执行
- 等待外部事件（开发提交修复）
- 出测门禁确保质量

#### 场景 3: 文档生成流程

**角色**：技术写作团队
**流程**：
```
提取 API → 生成文档 → 人工审查 → 发布
  ↓         ↓         ↓         ↓
自动      自动      审批      审批
```

**需求**：
- 确保所有必需文档生成
- 强制人工审查质量
- 记录审批历史

## 5. 功能需求

**需求描述**：用户可以通过 YAML 文件定义工作流。

**功能点**：
- F1.1: 定义步骤列表
- F1.2: 定义步骤依赖关系
- F1.3: 定义步骤输入输出

**优先级**：P0

#### F2: 状态机管理

**需求描述**：系统必须维护工作流和步骤的状态，并强制执行状态转换规则。

**功能点**：

## 7. 用户体验设计

### 7.1 CLI 设计原则

#### 原则 1: 一致性

所有命令遵循一致的命名和参数约定。

**示例**：
```bash
# 统一的模式
orchestrator <command> <project_dir> [options]

# 状态查询
orchestrator status <project_dir>

# 步骤操作
orchestrator start <project_dir> <step_id>
orchestrator complete <project_dir> <step_id>
orchestrator validate <project_dir> <step_id>

# 门禁操作
orchestrator approve <project_dir> <gate_id> --approver <name>
orchestrator reject <project_dir> <gate_id> --approver <name>
```

#### 原则 2: 渐进式披露

常用功能简单直接，高级功能可选。

**示例**：
```bash
# 简单用法（默认行为）
orchestrator next ./project

# 高级用法（可选参数）
orchestrator next ./project --auto-approve --timeout 3600
```

#### 原则 3: 清晰的反馈

每个操作都提供清晰的反馈。

**示例**：
```bash
$ orchestrator next ./project

✅ Started step: step1
  Token: TKN-A1B2C3D4
  Expires: 2025-01-22T19:30:45

  ℹ️  When done, run: orchestrator complete ./project step1
```

#### 原则 4: 友好的错误信息

错误信息必须清晰、可操作。

**示例**：
```bash
$ orchestrator next ./project

❌ Execution blocked by pending gates:
  - design_review
    Approve: orchestrator approve ./project design_review --approver <name>
```

### 7.2 配置文件设计

#### 原则 1: 约定优于配置

提供合理的默认值，减少配置负担。

**示例**：
```yaml
# workflow.yaml - 最小配置
id: my-workflow
name: 我的工作流
steps:
  - id: step1
    run: agent:worker
    outputs:
      - path: output/result.txt  # 默认 required=true
```

#### 原则 2: 声明式配置

配置描述"做什么"，而不是"怎么做"。

**示例**：
```yaml
# 声明式
steps:
  - id: step1
    run: agent:worker
    depends_on: [step0]  # 声明依赖

# 而不是命令式
steps:
  - id: step1
    run: agent:worker
    after:  # 不需要定义执行顺序
      - wait_for step0 to complete
      - check step0 status
```

#### 原则 3: 可验证性

配置文件必须可以验证。

**实现**：
```bash
# 验证工作流
$ orchestrator validate-workflow ./workflow.yaml

✅ Workflow structure is valid

⚠️  Warnings:
  - Step 'step3' has no outputs defined
```

### 7.3 错误处理

#### 原则 1: 快速失败

尽早发现和报告错误。

**示例**：
```bash
$ orchestrator init ./project --workflow workflow.yaml

❌ Project configuration validation failed:
  - Repository 'lee' path not found: /path/to/lee
  - Path alias '@output' references unknown repository 'lee'

Fix the errors above or use --skip-validation to bypass (not recommended)
```

#### 原则 2: 可操作的错误信息

错误信息必须告诉用户如何修复。

**示例**：
```bash
❌ MISSING OUTPUTS (2):
  - output/result.txt
  - output/data.json

Artifact Gate BLOCKED: 必须补齐所有必需输出后才能通过验证

💡 提示: Agent 应立即补齐缺失文件，然后重新运行 validate
```

#### 原则 3: 错误上下文

提供足够的错误上下文，帮助定位问题。

**示例**：
```bash
❌ Cannot start step step2: Dependency step1 not completed

Current state:
  - step1: completed
  - step2: pending (blocked)
  - step3: pending

Dependencies:
  - step2 depends on: [step1]

💡 Troubleshooting:
  1. Check if step1 actually completed: orchestrator status ./project
  2. Verify step1 outputs: ls -la output/
  3. Reset step2 if needed: orchestrator reset ./project step2
```

### 7.4 文档设计

#### 原则 1: 结构化

文档必须有清晰的结构。

**结构**：
1. 快速开始（5 分钟上手）
2. 核心概念（理解系统）
3. 完整指南（深入学习）
4. 示例（参考实现）
5. API 参考（技术细节）

#### 原则 2: 示例驱动

每个功能都有完整的示例。

**示例**：
```markdown
## 审批门禁

### 基本用法

```bash
$ orchestrator approve ./project design_review --approver "张三"
```

### 带评论

```bash
$ orchestrator approve ./project design_review \
  --approver "张三" \
  --comment "设计文档符合要求，可以继续"
```

### 输出

```
✅ Gate design_review approved
  Approval ID: APPR-12345678
  Approver: 张三
```
```

#### 原则 3: 多种格式

支持多种学习风格的文档。

**格式**：
- 文字教程（详细说明）
- 示例代码（实战演练）
- 图表（可视化）
- 视频（演示讲解）
