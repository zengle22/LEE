## 三、主要功能与流程

### 3.1 核心执行流程

```
用户输入 (CLI/API)
    ↓
Orchestrator.create_workflow()
    ↓ ← ContractDiscovery.validate_workflow_inputs() ✅ 已集成
StateMachine 初始化状态
    ↓
while 有 ready steps:
    step = get_ready_step()
    ↓
    ToolGuard.issue_token(step) ✅ 已集成
    ↓
    executor = ExecutorFactory.get(step.type)
    ↓
    RetryExecutor.execute() ← 支持指数退避 ✅ NEW
    ↓
    VariableResolver.resolve_all() ← 解析 $inputs/$sX_yyy ✅ NEW
    ↓
    result = await executor.execute(input_data)
    ↓
    Trace.record_span() ← Span 追踪记录 ✅ NEW
    ↓
    StateMachine.update_state(result)
    ↓
    if 需要 gate 审批:
        → GateEngine / HumanApproval 等待
    ↓
    检查是否需要 spawn 子workflow
    ↓
Workflow 完成/失败
```

## 五、当前功能缺失与差距

> **评审说明**: 本章优先级经架构评审后重新排序，原则为"价值/成本比优先"而非"技术吸引力优先"。

### 5.1 高优先级 (P1) — 影响投产可靠性

| 缺失功能 | 优先级 | 状态 | 不做的后果 |
|---------|:------:|------|-----------|
| **Retry/Trace 集成到执行链** | P1 | 模块已实现但未挂载到主路径 | 已写好的 2,300 行代码成为死代码，LLM 调用失败无自动恢复 |
| **Contract Schema 输出校验** | P1 | `validators/schema_validator.py` 已实现，未在步骤完成后调用 | 只校验入口不校验出口，37 个 contract 约束力减半 |
| **Agent 规范 LRU 缓存** | P1 | `agent_loader.py` (14K) 未实现缓存 | 每次步骤执行重复解析 YAML，多步骤工作流性能退化 |
| **新模块单元测试** | P1 | `retry.py`/`trace.py`/`variable_resolver.py`/`state_machine_executor.py` 无独立测试 | 2,400 行核心代码无回归保护 |

### 5.2 中优先级 (P2) — 影响架构健康

| 缺失功能 | 优先级 | 状态 | 不做的后果 |
|---------|:------:|------|-----------|
| **step_runners.py 策略模式重构** | P2 | 当前 967行/36K，是新的"上帝 Mixin" | 每次修改一种 step type 都可能影响其他类型，regression 风险高 |
| **runtime/executor/ 路径定性** | P2 | 与 `orchestrator/execution/` 并存，18 个文件无明确边界 | 两套代码维护不一致，新人困惑，选型无据 |
| **Gate 审批下游依赖检查** | P2 | `gate_engine.py` 部分实现 | 审批通过后下游步骤可能未正确解锁 |
| **Workflow on_failure 策略** | P2 | 未实现 skip / fallback 策略 | 步骤失败只能重试或整体终止，无法优雅降级 |
| **配置外部化** | P2 | `project_config.py` 30K，参数硬编码 | 修改 token 限制、超时、重试次数需改代码而非配置文件 |

### 5.3 低优先级 (P3) — 影响规模化运营

| 缺失功能 | 优先级 | 状态 | 不做的后果 |
|---------|:------:|------|-----------|
| **并行步骤执行** | P3 | `state_machine.py` 不支持 parallel step | 性能受限但当前 17 个 workflow 均为串行设计，暂无阻塞 |
| **事件日志分片** | P3 | SQLite 单表存储 | 大工作流日志查询变慢 |
| **Span 追踪可视化 UI** | P3 | `trace.py` 有数据但无前端 | 开发者只能看 JSONL 原始数据 |
| **契约版本管理** | P3 | 当前 contract 只有 v1 | 未来 schema 升级无迁移机制 |
| **OpenTelemetry 导出** | P3 | 未对接标准 | 无法接入统一监控平台 |

> **关于并行步骤的降级说明**: 并行调度引入的复杂度（fork/join、部分成功回滚、Gate 阻塞并行分支）远超收益。L3 workflow 本质是流水线（设计→编码→测试→review），天然串行。建议有明确性能瓶颈数据后再提升优先级。

## 六、架构层面改进建议

### 6.1 当前架构亮点

1. **Mixin 重构成功**: `orchestrator.py` 从 1645行 大幅瘦身到 627行，职责分离清晰
2. **IR 中间层引入**: 解耦 YAML spec 解析与执行逻辑，为后续优化提供良好基础
3. **治理能力增强**: ContractDiscovery + ToolGuard + Trace 三位一体
4. **执行器生态扩展**: 从 3 种执行器扩展到 6 种（含 ClaudeCodeExecutor）

### 6.2 仍需关注的架构问题

**问题 1: step_runners.py "上帝 Mixin" 风险**

`step_runners.py` (967行/36K) 依赖了 `agent_loader`、`agent_context_builder`、`executors`、`gate_engine`、`variable_resolver`、`contract_discovery` 等几乎所有模块。Mixin 拆分解决了 `orchestrator.py` 的问题，但复杂度只是转移而非消除。

**推荐方案**: 用策略模式替代 Mixin 中的 step type 分支：

```python
# 策略接口
class StepRunnerStrategy(ABC):
    async def execute(self, step, context) -> StepResult: ...

# 按 step type 拆分
class LLMStepRunner(StepRunnerStrategy): ...
class GateStepRunner(StepRunnerStrategy): ...
class SubworkflowStepRunner(StepRunnerStrategy): ...

# orchestrator 只做分发
runner = self.runner_registry.get(step.type)
result = await runner.execute(step, context)
```

**问题 2: 执行器双路径 — 需要架构决策而非文档化**

`orchestrator/execution/` 与 `runtime/executor/` 并存不是文档问题，是架构决策问题。

**推荐决策**: `runtime/executor/` 定位为 **LangGraph 实验性路径**，标记 `experimental`。所有生产工作流走 `orchestrator/execution/`。长期评估后二选一：
- 如果 LangGraph 路径成熟 → 迁移为主路径
- 如果 Orchestrator 路径满足需求 → 淘汰 `runtime/executor/`

**问题 3: 已实现模块的"最后一公里"集成**

Retry、Trace、Schema Validator 均已实现但未接入执行主链路。根本原因是缺少 **executor 管道 (pipeline)** 抽象——每个横切关注点（重试、追踪、校验）都在不同位置手动挂载。

**推荐方案**: 引入 executor 中间件/装饰器模式：

```python
# 执行管道: Trace → Retry → Validate → Execute
pipeline = ExecutionPipeline([
    TraceMiddleware(tracer),
    RetryMiddleware(retry_policy),
    SchemaValidationMiddleware(validator),
])
result = await pipeline.execute(executor, step, context)
```
