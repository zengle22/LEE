# 试点代建服务说明书

## 1. 服务定位

本服务用于帮助客户在一个小范围真实场景中，跑通 AI 研发治理最小闭环。

一句话定位：

`选择一个真实 FEAT 或一个真实 release，帮助团队建立一条正式、可追溯、可验收的 AI 交付路径。`

这不是全量平台实施，也不是长期咨询项目。  
这是一个范围明确、目标明确、可验证结果的试点项目。

## 2. 服务目标

试点要验证的不是“理念是否正确”，而是：

- 团队当前问题是否真能通过治理方式缓解
- 哪条路径最值得先标准化
- 哪些对象、流程、证据和复盘机制应该先做硬

## 3. 适合的试点范围

优先选择以下 4 类试点之一：

### 方案 A：单 FEAT 黄金路径

范围：

- 从正式输入到 Dev、QA、release 判断，跑通一个 FEAT

适合：

- 需求边界和交付边界都比较混乱的团队

### 方案 B：QA Harness 治理试点

范围：

- 建立 `TASK -> TESTPLAN -> RELEASE` 的正式 QA 执行入口和证据收口

适合：

- 测试执行混乱、结论不正式的团队

### 方案 C：Dev Workflow 改造试点

范围：

- 建立 `TECH -> Contract -> Impl -> Integration -> Evidence` 的最小主流程

适合：

- 开发侧路径漂移明显、返工率高的团队

### 方案 D：Release Governance 试点

范围：

- 建立 release scope、test plan、evidence 和 go/no-go 判断机制

适合：

- 发版决策靠经验、缺乏正式依据的团队

## 4. 标准交付内容

根据试点范围，标准交付通常包括：

- 试点边界和目标定义
- 一条正式对象链或主流程样板
- 关键模板或 schema
- 一套试点操作手册
- 1 个真实样例
- 试点复盘报告
- 下一步扩展建议

## 5. 交付流程

### Step 1：试点定义

- 明确试点对象
- 明确边界
- 明确完成标准

### Step 2：现状梳理

- 梳理当前对象、流程、角色分工
- 找到最小治理改造点

### Step 3：方案落地

- 定义正式对象和流程
- 调整或补充模板、样板、规则
- 接入最小执行路径

### Step 4：真实跑通

- 选择真实需求或真实版本验证
- 验证链路是否能跑通
- 暴露断点

### Step 5：复盘和交接

- 输出试点复盘
- 输出后续扩展建议
- 判断是否进入陪跑或二期

## 6. 建议完成标准

一次合格的试点，至少应满足：

- 有明确的正式输入边界
- 有明确的正式执行路径
- 有明确的 evidence 或 report 收口
- 可以对一次真实交付形成正式判断
- 团队知道下一步应该继续标准化哪部分

## 7. 客户协作要求

为保证试点有效，客户至少需要提供：

- 一个明确负责人
- 一个明确试点对象
- 最小必要资料
- 关键节点配合评审

如果客户无法提供这些条件，试点很容易沦为概念讨论，不建议启动。

## 8. 建议报价

### 小型试点

适合：

- 单一 FEAT
- 单一流程问题
- 快速验证

建议价格：

- RMB 10000 - 30000

### 中型试点

适合：

- 需要跨 Product / Dev / QA 协同
- 需要至少一条真实链路跑通

建议价格：

- RMB 30000 - 80000

### 深度试点

适合：

- 客户已有明确中期落地意愿
- 需要较完整的试点包和下一阶段路线图

建议价格：

- RMB 80000+

## 9. 续单路径

试点后可转化为：

- 月度治理陪跑
- 第二条路径扩展
- 标准模板包采购
- 私有增强和更深集成

## 10. 销售表达建议

不要说：

- 我们来帮你做完整 AI 软件工厂
- 我们要重构你们整个组织流程

建议说：

- 先帮你跑通一条真实交付路径
- 先在一个 FEAT 或一个 release 上验证最小治理闭环
- 先证明这套方法在你们团队里有效，再决定是否扩大范围

- 拿真实案例

- 提炼产品边界
- 为后续顾问订阅和产品化打基础
