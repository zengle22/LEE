# AI 研发治理诊断服务说明

## 1. 服务定位

本服务面向已经在团队中使用 AI 辅助研发，但流程开始失控、返工增加、交付不可追溯的团队。

服务目标不是帮客户“换一个 AI 工具”，而是帮助客户识别并修复以下问题：

- 需求、开发、测试之间没有正式真相源
- AI 可以绕过正式输入和流程边界直接开工
- 做完了但证据不完整，无法做 release 级判断
- 团队每次踩坑都在重复，没有形成系统化经验

一句话说明：

`帮助团队找出 AI 研发中的治理断点，并给出最短修复路径。`

## 2. 适合的客户

适合：

- 10 - 100 人技术团队
- 已广泛使用 Claude / Cursor / Copilot / Codex / Qwen 等工具
- 产品、开发、测试 handoff 已出现混乱
- 需要更正式的 release、evidence、QA、复盘机制

不适合：

- 只想要 prompt 优化建议的个人用户
- 只想买培训、不打算落地试点的团队
- 需要长期重型咨询项目的大型复杂组织

## 3. 诊断范围

默认诊断 5 个维度：

- SSOT 与正式对象边界
- Dev workflow 质量与路径漂移
- QA harness / test execution 入口治理
- release / evidence / go-no-go 机制
- 复盘、知识沉淀与流程进化机制

可选加项：

- 开源与商业化路线建议
- 组织内 AI 工具使用策略
- 多模型/多 Agent 路由和治理策略

## 4. 典型问题样例

诊断通常会识别这类问题：

- FEAT、TASK、TESTSET、TESTPLAN 语义混乱
- workflow 入口过多，团队不知道哪条是主路径
- AI 直接从 prompt 开工，没有正式对象约束
- QA 执行只关注脚本和跑批，没有 release 级判定
- release 前缺乏统一 evidence 收口
- 复盘只是会议纪要，没有进入下次流程

## 5. 交付内容

标准交付包含：

- 1 份《AI 研发治理诊断报告》
- 1 份《高风险问题清单》
- 1 份《30/60/90 天改造建议》
- 1 张《最小治理闭环建议图》
- 1 次诊断汇报会议

诊断报告建议结构：

1. 当前使用现状
2. 关键治理断点
3. 风险优先级排序
4. 最短修复路径
5. 推荐试点范围
6. 预期收益与风险

## 6. 服务流程

### Step 1：前置沟通

- 了解团队规模、角色分工、当前 AI 使用方式
- 判断是否存在真实治理痛点
- 明确诊断范围和边界

### Step 2：资料收集

建议收集：

- 当前研发流程说明
- 样例需求 / 样例 release
- 测试流程与交付方式
- 现有 AI 使用规则或约定

### Step 3：诊断分析

分析重点：

- 对象边界是否清晰
- 输入边界是否正式
- 执行路径是否稳定
- QA 是否具备正式验证入口
- evidence 是否支持 release 判定
- 经验是否能沉淀和复用

### Step 4：报告交付

- 输出结构化报告
- 讲清楚问题和建议
- 明确哪些属于 P0，哪些属于后续优化项

### Step 5：后续转化

可选续单方向：

- 黄金路径试点代建
- QA harness 接入
- Dev workflow 改造
- 月度陪跑顾问

## 9. 对外销售话术

不建议这样说：

- 我们有三轴 SSOT
- 我们有 L1/L2/L3 软件工厂框架
- 我们是 AI 软件工厂平台

建议这样说：

- 帮你找出团队现在 AI 研发中最贵的返工点
- 帮你把 AI 研发从失控状态变成可追溯流程
- 帮你找出为什么做完了却无法稳定验收和发版
- 先不改全公司，只帮你跑通一条真实交付路径

## 10. 成功标准

一次成功的诊断不只是“报告写完”，而是：

- 客户认同问题确实存在
- 客户认可优先级排序
- 客户愿意基于建议继续推进试点
- 诊断结论足够清晰，可转化为下一阶段付费项目
