## 4. 痛点区文案

**标题**

AI 研发失控，通常不是因为模型不够强

**说明**

真正的问题通常来自流程治理缺失，而不是模型能力缺失。

**痛点 1**

需求、开发、测试之间没有正式真相源  
结果是每个角色都在基于不同版本的理解工作。

**痛点 2**

AI 可以绕过正式输入和流程边界直接开工  
结果是“看起来做完了”，但无法正式验收。

**痛点 3**

没有统一 evidence 和 release 判断机制  
结果是做了什么、测了什么、为什么能发版说不清。

**痛点 4**

每次踩坑都停留在聊天记录和个人经验里  
结果是团队无法通过 AI 使用经验持续变强。

## 5. 产品方法区文案

**标题**

我们不只做 Agent，我们做 Agent 治理

**说明**

LEE 的核心不是让 Agent 获得更多行动自由，而是让 Agent 在正式对象、正式流程和正式证据中工作。

**方法 1：正式真相源**

通过 SSOT 对象把需求轴、交付轴、证据轴分开，避免语义混乱。

**方法 2：正式执行边界**

通过 workflow-first 和 gate 机制，阻止 AI 绕过正式流程直接开工。

**方法 3：正式证据收口**

通过 evidence、report、release check 机制，把“做了什么”收敛成可审计结果。

**方法 4：正式复盘进化**

通过复盘与知识沉淀，让每次任务结果都能反哺下一次交付。

## 11. 对外介绍短版本

适合发给潜在客户或合作方的两段式介绍：

LEE 是一个面向 Product、Dev、QA 的 AI 研发治理项目。它不是单纯帮助团队“让 AI 写更多代码”，而是帮助团队建立正式输入、正式执行、正式证据和正式复盘机制，让 AI 参与研发时不再失控。

如果你的团队已经在大量使用 Claude、Cursor、Copilot 或 Codex，但开始遇到需求漂移、流程绕过、证据不完整、release 判断困难等问题，LEE 可以先从一次治理诊断或一个小范围试点开始切入。

## 12. 当前建议

在个人 OPC 阶段，首页文案建议优先使用“问题导向”版本，而不是“平台导向”版本。

原因：

- 用户更容易理解真实痛点
- 更容易导向诊断服务
- 更适合低成本获客
- 不会过早把项目包装成过重的平台产品
