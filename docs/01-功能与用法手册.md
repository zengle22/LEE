## 核心理念

### 问题陈述

传统AI工作流面临的核心挑战：

```
┌────────────────────────────────────────────────────────────┐
│  问题                     │  传统方式依赖                │
├────────────────────────────────────────────────────────────┤
│  Agent编排可能被跳过      │  LLM的"自觉性"               │
│  人类门禁可能被忽略       │  提示词约束                   │
│  产物验证可能被遗漏       │  Agent主动记录                │
│  执行日志可能不完整       │  Agent良好习惯                │
└────────────────────────────────────────────────────────────┘
```

### Orchestrator的解决方案

**让规范从"建议"变成"协议"**

- ✅ **强制执行** - 通过状态机和令牌系统，而非依赖LLM自律
- ✅ **门禁产物化** - 审批变成依赖产物，下游步骤强依赖
- ✅ **自动溯源** - 编排器自动记录事件流，不依赖Agent
- ✅ **能力隔离** - 通过令牌控制工具权限，防止越权操作

## 主要功能

### 1. 状态机管理

**维护工作流的完整生命周期状态**

```yaml
运行状态 (RunState):
  - created: 工作流已创建
  - running: 正在执行
  - paused: 等待门禁审批
  - waiting_external: 等待外部事件（如开发修复）
  - looping: 循环执行中（测试流程）
  - completed: 执行完成
  - failed: 执行失败
  - aborted: 已中止

步骤状态 (StepState):
  - pending: 等待执行
  - blocked: 被依赖阻断
  - ready: 可以执行
  - in_progress: 执行中
  - validating: 验证中
  - gate_pending: 等待门禁
  - waiting_external: 等待外部事件
  - loop_iteration: 循环迭代中
  - completed: 已完成
  - failed: 失败
  - skipped: 跳过
```

**依赖关系检查**
- 自动计算步骤依赖树
- 阻止非法状态转换
- 强制执行前置条件

### 2. Step Token 令牌系统

**授权和权限控制机制**

```
令牌特性:
├── 短期有效 (默认4小时)
├── 绑定到具体步骤
├── 签名防伪造
├── 细粒度权限控制
└── 可撤销
```

**工具权限矩阵:**

| 权限类型 | 工具列表 | 需要令牌 | 需要审批 |
|---------|---------|---------|---------|
| read | Read, Glob, Grep, WebFetch | ❌ | ❌ |
| write | Write, Edit, NotebookEdit | ✅ | ❌ |
| execute | Bash, Task | ✅ | ❌ |
| deploy | Bash:kubectl, Bash:docker | ✅ | ✅ |
| commit | Bash:git commit, Bash:git push | ✅ | ✅ |

### 3. Agent自动调度（v1.2+）

**自动加载和注入Agent规范**

工作流程：
```
1. orchestrator start <step_id>
   ↓
2. 从 workflow.yaml 读取 step.run (agent_id)
   ↓
3. 加载 ai-spec/specs/common/agents/{agent_id}/v1/agent.yaml
   ↓
4. 构建完整上下文（包含persona、质量标准、决策规则）
   ↓
5. 注入到 .workflow/current-context.yaml
   ↓
6. AI工具读取并遵循上下文执行
```

**Agent Spec结构:**
```yaml
id: agent.dev.requirement_calibrator
name: Requirement Calibrator
version: "1.0"

persona:
  role: 资深产品需求专家
  style: 逻辑严谨、粒度精细
  tone: professional, detail-oriented

prompting:
  system: |
    You are a Requirement Calibrator...
  instructions:
    - 必须校准每个模块的需求粒度
    - 识别缺失的前置条件

policy:
  quality_bar:
    must_have:
      - 必须覆盖所有用户场景
      - 每个模块有明确验收标准
  decision_rules:
    - condition: 需求粒度过粗
      action: 拆分为更小的功能点

responsibility:
  in_scope:
    - 需求校准和细化
    - 识别缺失需求
  out_of_scope:
    - 不做技术设计
    - 不编写代码

forbidden_behaviors:
  - 不可跳过需求校准直接实现
  - 不可修改已冻结的分析文件

contracts:
  input_schema: "@/contracts/product-modules/v1/schema.json"
  output_schema: "@/contracts/calibrated-requirements/v1/schema.json"
```

### 4. 验证器引擎

**自动产物验证，fail-fast机制**

内置验证器：

```python
SchemaValidator:
  # JSON Schema 验证
  用途: 验证产物符合契约格式
  示例: 验证 PRD JSON 符合 product-spec schema

FileValidator:
  # 文件存在性验证
  用途: 确保所需文件已创建
  示例: 验证 test_report.json 存在

CoverageValidator:
  # 覆盖率验证
  用途: 验证测试覆盖率达标
  示例: 覆盖率 >= 80%

CustomValidator:
  # 自定义脚本验证
  用途: 执行自定义检查逻辑
  示例: 运行 pylint 检查代码质量
```

验证失败动作：
- `block`: 阻止流程继续（默认）
- `warn`: 仅警告，允许继续
- `retry`: 自动重试步骤

### 5. 门禁管理

**人工和自动审批机制**

门禁类型：

**人工门禁 (Human Gate)**
```yaml
human_gate:
  id: h1_requirement_review
  type: human
  blocking: true
  timeout_hours: 24
  required_roles: [product_manager, tech_lead]
  min_approvals: 2
  timeout_action: escalate
```

**自动门禁 (Auto Gate)**
```yaml
quality_gate:
  id: a1_test_coverage
  type: auto
  blocking: true
  condition: "coverage >= 0.80"
  validators:
    - type: coverage
      config:
        threshold: 0.80
```

门禁状态：
- `pending`: 等待审批
- `approved`: 已通过
- `rejected`: 已拒绝
- `timeout`: 超时

### 6. 事件溯源与追踪

**完整的执行历史记录**

#### 事件日志 (Event Log)
存储位置: `.workflow/events.jsonl`

事件类型：
```python
# 运行级事件
RUN_CREATED, RUN_STARTED, RUN_PAUSED, RUN_COMPLETED, RUN_FAILED

# 步骤级事件
STEP_READY, STEP_STARTED, STEP_COMPLETED, STEP_FAILED

# 验证事件
VALIDATION_STARTED, VALIDATION_PASSED, VALIDATION_FAILED

# 门禁事件
GATE_TRIGGERED, GATE_APPROVED, GATE_REJECTED

# 产物事件
ARTIFACT_CREATED, ARTIFACT_VALIDATED

# 令牌事件
TOKEN_ISSUED, TOKEN_VALIDATED, TOKEN_EXPIRED

# 工具调用事件
TOOL_CALLED, TOOL_BLOCKED
```

#### Span追踪 (Trace Log)
存储位置: `.workflow/traces/traces.jsonl`

基于Execution Trace Contract v1.0实现：
```yaml
Span类型:
  - orchestrator: 编排器操作
  - agent: Agent调用
  - tool: 工具调用
  - gate: 门禁检查
  - validation: 验证操作
  - io: IO操作

追踪特性:
  - 嵌套span支持（parent_span_id）
  - 自动计算duration
  - 自动脱敏敏感数据
  - 输入输出hash记录
  - 产物关联
```

### 7. 循环和外部等待（v1.3+）

**支持测试流程等迭代场景**

#### 循环控制
```yaml
loop:
  id: bug_fix_verification_loop
  condition: "has_failing_tests"
  max_iterations: 10
  body_steps:
    - step1_run_tests
    - step2_analyze_failures
    - step3_fix_bugs
```

命令：
```bash
# 开始循环
python -m orchestrator loop-start ./project bug_fix_loop

# 完成当前迭代
python -m orchestrator loop-complete ./project bug_fix_loop --continue

# 结束循环
python -m orchestrator loop-complete ./project bug_fix_loop
```

#### 外部等待
```yaml
wait:
  id: wait_for_developer_fix
  event_type: developer_fixed_bug
  timeout: 48h
  timeout_action: escalate
  notify_channels: [slack, email]
```

命令：
```bash
# 创建等待
python -m orchestrator wait ./project step_5 --event developer_fixed_bug --timeout 48h

# 解决等待
python -m orchestrator resolve ./project wait_001 --resolver "张三" --data '{"fix_commit": "abc123"}'
```

### 8. Workflow生成器（v1.6）

**从模板生成标准化workflow.yaml**

防止AI简化或省略必需步骤：

```python
generator = WorkflowGenerator("templates/phase-openspec-flow.yaml")

config = PhaseConfig(
    id="phase11-logging",
    name="日志体系改造",
    phase_dir="project/AI跑步教练/dev/phase11",
    step_descriptions={
        "p2_requirement_calibration": "校准日志改造需求"
    }
)

result = generator.generate(config, output_path="./workflow.yaml")
```

强制要求：
- ✅ 所有必需步骤必须存在（REQUIRED_STEPS）
- ✅ 依赖关系不可修改
- ✅ 门禁配置不可删除
- ⚠️ 仅允许修改描述、路径等非结构性字段

## 命令行接口

### 基础命令

#### 初始化工作流
```bash
python -m orchestrator init <project_dir> --workflow <workflow.yaml>

# 示例
python -m orchestrator init ./my-project --workflow phase8-workflow.yaml
```

#### 查看状态
```bash
python -m orchestrator status <project_dir> [--json] [--verbose]

# 输出示例
════════════════════════════════════════════════════════════
  Workflow Status
════════════════════════════════════════════════════════════

Run ID: RUN-20260116-143022
State: RUNNING
Current Step: p2_requirement_calibration
Progress: 2/13 steps (15%)

Pending Gates:
  ⏳ h1_requirement_review (Human Gate - pending)

Ready Steps:
  ✅ p3_test_contract

Next Action: WAIT_FOR_APPROVAL
Next Step Human Gate: true
```

#### 开始步骤
```bash
python -m orchestrator start <project_dir> <step_id> [--agent <name>] [--inject-context] [--injector <name>]

# 示例
python -m orchestrator start ./project p2_requirement_calibration --inject-context

# 输出
✅ Step 'p2_requirement_calibration' started
🎫 Token issued: TKN-A3F2E1D8
⏱️  Valid until: 2026-01-16 18:30:22
📝 Agent context injected to .workflow/current-context.yaml
```

参数说明：
- `--inject-context`: 自动注入Agent上下文到AI工具
- `--injector <name>`: 指定injector (默认: claude_code)
- `--agent <name>`: 覆盖agent_id

#### 完成步骤
```bash
python -m orchestrator complete <project_dir> <step_id> [--outputs file1,file2]

# 示例
python -m orchestrator complete ./project p2_requirement_calibration \
    --outputs "calibrated-requirements.json,requirement-gaps.md"
```

#### 验证产物
```bash
python -m orchestrator validate <project_dir> <step_id>

# 输出
✅ Validation passed
  - Schema validation: PASSED
  - File existence: PASSED (2 files)
  - Coverage check: PASSED (85%)
```

#### 审批门禁
```bash
# 通过
python -m orchestrator approve <project_dir> <gate_id> --approver <name>

# 拒绝
python -m orchestrator reject <project_dir> <gate_id> --approver <name> --reason <reason>

# 示例
python -m orchestrator approve ./project h1_requirement_review --approver "张三"
```

### 令牌管理

```bash
# 获取步骤令牌
python -m orchestrator token <project_dir> <step_id>

# 检查令牌有效性
python -m orchestrator check <project_dir> --token <token_id> [--tool <tool_name>]

# 示例
python -m orchestrator check ./project --token TKN-A3F2E1D8 --tool Write
```

### 日志与追踪

```bash
# 查看事件日志
python -m orchestrator log <project_dir> [--step <step_id>] [--limit <n>]

# 查看追踪
python -m orchestrator trace <project_dir> [--format markdown|yaml]

# 导出审计报告
python -m orchestrator export <project_dir> --format json|yaml

# 示例
python -m orchestrator log ./project --limit 20
python -m orchestrator trace ./project --format markdown > trace_report.md
```

### Agent上下文

```bash
# 查看当前注入的Agent上下文
python -m orchestrator context <project_dir> [--injector <name>]

# 清除上下文
python -m orchestrator context <project_dir> --clear

# 示例
python -m orchestrator context ./project
```

### 测试流程扩展（v1.3）

```bash
# 循环控制
python -m orchestrator loop-start <project_dir> <loop_id>
python -m orchestrator loop-complete <project_dir> <loop_id> [--continue]

# 外部等待
python -m orchestrator wait <project_dir> <step_id> --event <event_type> [--timeout 48h]
python -m orchestrator resolve <project_dir> <wait_id> --resolver <name> [--data <json>]

# Loop Back (从失败门禁回退)
python -m orchestrator loop-back <project_dir> <from_step> <to_step> [--reason <reason>]
```

## 工作流定义

### workflow.yaml 基本结构

```yaml
kind: phase-workflow
version: "1.5"
id: phase8-ui-pages
name: Phase 8 - UI页面实现

# 工作流元数据
metadata:
  owner: dev-team
  project: AI跑步教练
  phase_dir: project/AI跑步教练/dev/phase8

# 前置条件（可选）
preconditions:
  - exists: "@/phase7-api-implementation/API实现报告.md"
    message: "需要先完成API实现"

# 强制执行规则
enforcement:
  fail_on_validation_error: true
  require_all_gates: true
  block_on_missing_deps: true

# 人机协作配置
human_in_the_loop:
  - step_id: p11_phase_acceptance
    reason: "最终验收需要人类确认"
    required: true

# 步骤定义
steps:
  - id: p1_openspec_init
    name: OpenSpec提案初始化
    run: agent.dev.openspec_initiator
    depends_on: []

    inputs:
      - source: external
        path: "@/phase7/API实现报告.md"
        required: true

    outputs:
      - path: "@/phase8/openspec/PROPOSAL.md"
        contract_ref: openspec-proposal-v1
        required: true

    validators:
      - type: schema
        config:
          schema_path: "@/contracts/openspec-proposal/v1/schema.json"
        fail_action: block

    on_success:
      - log_event: "OpenSpec初始化完成"

    on_failure:
      action: retry
      max_retries: 2

  - id: p2_requirement_calibration
    name: 需求校准
    run: agent.dev.requirement_calibrator
    depends_on: [p1_openspec_init]

    human_gate:
      id: h1_requirement_review
      type: human
      blocking: true
      timeout_hours: 24
      required_roles: [product_manager]
      min_approvals: 1

  # ... 更多步骤

# 产物清单
deliverables:
  - name: "UI页面实现代码"
    path: "@/src/pages/**/*.tsx"
    type: source_code

  - name: "单元测试"
    path: "@/tests/**/*.test.tsx"
    type: test_code

# 质量标准
quality_standards:
  - name: "测试覆盖率"
    threshold: 0.80
    validator: coverage

  - name: "代码审查通过"
    validator: code_review
    required: true
```

### Step定义详解

```yaml
id: p5_implementation             # 步骤唯一标识
name: 功能实现                     # 人类可读名称
description: 实现UI组件和页面逻辑  # 详细描述（可选）

run: agent.dev.implementation_engineer  # Agent引用

depends_on:                       # 前置依赖
  - p4_openspec_proposal
  - p3_test_contract

parallel_with: []                 # 可并行执行的步骤

inputs:                           # 输入定义
  - source: p4_openspec_proposal
    path: "@/openspec/PROPOSAL.md"
    required: true
    schema_ref: openspec-proposal-v1

outputs:                          # 输出定义
  - path: "@/src/pages/HomePage.tsx"
    contract_ref: react-component-v1
    required: true
    freeze: false                 # 是否冻结保护

validators:                       # 验证器列表
  - type: file_exists
    config:
      files: ["@/src/pages/HomePage.tsx"]

  - type: custom
    config:
      command: "npm run lint"
      expect_exit_code: 0

execution_model: prompt_switch    # 执行模型
timeout_minutes: 60               # 超时时间

mandatory: true                   # 是否必须
skip_allowed: false               # 是否允许跳过
skip_condition: null              # 跳过条件

human_gate:                       # 人工门禁（可选）
  id: h2_code_review
  type: human
  blocking: true

quality_gate:                     # 质量门禁（可选）
  id: a2_test_passing
  type: auto
  condition: "test_result.pass_rate >= 0.95"

on_success:                       # 成功后动作
  - log_event: "实现完成"
  - trigger_step: p6_unit_test

on_failure:                       # 失败后动作
  action: retry
  max_retries: 3
  retry_delay: 300

remediation:                      # 补救措施
  - condition: "validation_failed"
    action: "人工介入修复"
```

### 路径别名 (@符号)

使用 `@` 前缀引用项目相对路径：

```yaml
# 在 workflow.yaml 中
outputs:
  - path: "@/phase8/实现报告.md"  # 实际: project/AI跑步教练/dev/phase8/实现报告.md

# 在 project.yaml 中配置基础路径
project:
  root: /absolute/path/to/project/AI跑步教练/dev
```

## Agent自动调度

### 工作原理

```
┌──────────────────────────────────────────────────────────┐
│                     Agent调度流程                         │
├──────────────────────────────────────────────────────────┤
│                                                           │
│  1. orchestrator start step_id                          │
│     ↓                                                     │
│  2. 读取 workflow.yaml 的 step.run                       │
│     ↓                                                     │
│  3. AgentResolver 解析 agent_id                          │
│     ├─ 查找 ai-spec/specs/common/agents/{id}/v1/         │
│     └─ 回退到 ai-spec/cli/claude/agents/{id}.md          │
│     ↓                                                     │
│  4. AgentLoader 加载 agent.yaml                          │
│     ├─ 解析 persona, policy, prompting                   │
│     ├─ 验证格式                                           │
│     └─ 提取 contracts, forbidden_behaviors               │
│     ↓                                                     │
│  5. AgentContextBuilder 构建上下文                       │
│     ├─ 整合 step metadata                                │
│     ├─ 整合 workflow metadata                            │
│     └─ 生成 AgentContext 对象                            │
│     ↓                                                     │
│  6. AgentInjector 注入上下文                             │
│     ├─ Claude Code: 写入 .workflow/current-context.yaml  │
│     ├─ Codex: 注入到 system prompt                       │
│     └─ Gemini: 注入到 system instruction                 │
│     ↓                                                     │
│  7. AI工具读取并遵循上下文执行                            │
│                                                           │
└──────────────────────────────────────────────────────────┘
```

### 上下文注入格式

`.workflow/current-context.yaml` 示例：

```yaml
step:
  id: p2_requirement_calibration
  name: 需求校准
  description: 校准需求粒度，识别缺失需求
  inputs:
    - "@/phase7/产品模块定义.json"
  outputs:
    - "@/phase8/校准后需求.json"
    - "@/phase8/需求差距分析.md"

agent:
  id: agent.dev.requirement_calibrator
  name: Requirement Calibrator
  version: "1.0"

  system_prompt: |
    You are a Requirement Calibrator, specialized in refining product requirements.
    Your role is to ensure requirements are granular, complete, and actionable.

  persona:
    role: 资深产品需求专家
    style: 逻辑严谨、粒度精细
    tone: professional

  forbidden_behaviors:
    - 不可跳过需求校准直接实现
    - 不可修改已冻结的分析文件
    - 不可简化或合并需求粒度

  quality_bar:
    - 必须覆盖所有用户场景
    - 每个模块有明确验收标准
    - 需求粒度足够细，每个点可独立实现

  responsibility:
    in_scope:
      - 需求校准和细化
```

```yaml
validators:
  - type: schema
```

```yaml
validators:
  - type: file_exists
    config:
      files:
        - "@/src/HomePage.tsx"
        - "@/tests/HomePage.test.tsx"
    fail_action: block
```

#### Coverage Validator
```yaml
validators:
  - type: coverage
    config:
      threshold: 0.80
      coverage_file: "@/coverage/coverage.json"
    fail_action: block
```

#### Custom Validator
```yaml
validators:
  - type: custom
    config:
      command: "npm run lint"
      expect_exit_code: 0
      timeout: 300
    fail_action: warn
```

### 验证失败处理

```yaml
validators:

on_failure:
```

## 门禁系统

### 人工门禁工作流

```
1. 步骤完成 → 触发人工门禁
   ↓
2. orchestrator 状态变为 PAUSED
   ↓
3. 通知审批人（通过外部系统）
   ↓
4. 审批人执行:
   python -m orchestrator approve <gate_id> --approver "张三"
   ↓
5. 审批产物化:
   创建 .workflow/approvals/{gate_id}.yaml
   ↓
6. 下游步骤依赖此审批产物
   ↓
7. orchestrator 状态恢复为 RUNNING
```

### 审批产物结构

`.workflow/approvals/h1_requirement_review.yaml`:
```yaml
gate_id: h1_requirement_review
step_id: p2_requirement_calibration
status: approved
approver: 张三
approved_at: "2026-01-16T15:30:00"
comment: "需求粒度合理，可以进入实现阶段"
artifact_hash: a3f2e1d8c4b5a6f7
```

### 自动门禁

```yaml
quality_gate:
  id: a1_test_coverage
  type: auto
  blocking: true
  condition: "coverage >= 0.80"

  validators:
    - type: coverage
      config:
        threshold: 0.80

  on_pass:
    - log_event: "质量门禁通过"

  on_fail:
    action: block
    message: "测试覆盖率不足，需要补充测试"
```

## 追踪与审计

### 事件日志查询

```bash
# 查看所有事件
python -m orchestrator log ./project

# 查看特定步骤的事件
python -m orchestrator log ./project --step p2_requirement_calibration

# 查看最近20条
python -m orchestrator log ./project --limit 20

# 导出JSON格式
python -m orchestrator export ./project --format json > audit.json
```

### Span追踪分析

```bash
# 生成Markdown追踪报告
python -m orchestrator trace ./project --format markdown > trace.md

# YAML格式
python -m orchestrator trace ./project --format yaml > trace.yaml
```

追踪报告包含：
- Run级别统计（总时长、步骤数）
- 每个步骤的Span详情
- 工具调用记录
- 验证和门禁事件
- 错误和重试记录

### 审计要点

1. **产物溯源**: 每个产物有创建时间、创建Agent、输入hash
2. **工具调用**: 所有外部操作有记录（读写文件、执行命令）
3. **门禁追踪**: 审批人、时间、理由
4. **验证结果**: 每个验证器的详细结果
5. **错误历史**: 失败原因、重试次数

## 最佳实践

### 1. 工作流设计原则

✅ **单一职责**: 每个步骤只做一件事
✅ **明确依赖**: 显式声明所有前置依赖
✅ **产物契约化**: 定义清晰的输入输出schema
✅ **验证前置**: 验证器在步骤定义时就配置好
✅ **门禁合理**: 仅在关键决策点设置人工门禁

❌ **避免**:
- 隐式依赖（依赖未声明的产物）
- 过度门禁（每个步骤都要审批）
- 弱验证（仅检查文件存在）
- 循环依赖

### 2. Agent规范编写

✅ **清晰的角色定义**: persona要具体
✅ **明确的禁止行为**: 列出所有违规场景
✅ **可量化的质量标准**: quality_bar要可验证
✅ **边界清晰**: in_scope和out_of_scope明确

### 3. 令牌管理

✅ **最小权限原则**: 仅授予必要的工具权限
✅ **短期有效**: 使用默认4小时有效期
✅ **及时撤销**: 步骤完成后自动失效

### 4. 验证策略

✅ **多层验证**: 格式 + 语义 + 业务规则
✅ **fail-fast**: 验证失败立即阻断
✅ **可重试**: 允许修复后重新验证

### 5. 门禁设计

✅ **关键节点**: 仅在架构决策、安全审查等关键点设置
✅ **明确审批人**: 指定角色和最小审批数
✅ **超时处理**: 配置合理的超时策略

### 6. 追踪和调试

✅ **启用详细日志**: 开发阶段使用 `--verbose`
✅ **定期导出审计**: 每个phase结束后导出trace
✅ **错误复盘**: 分析事件日志定位问题

## 常见问题

### Q1: LLM忽略了工作流规则怎么办？

**A**: 加强系统提示词中的强制性语言：
```
MUST check workflow state before ANY operation
NEVER bypass gates or skip steps
FAIL if token is invalid
```

### Q2: 令牌总是过期？

**A**: 调整有效期或在步骤开始时刷新：
```bash
# 在 step 开始时重新获取令牌
python -m orchestrator start . <step_id>
```

### Q3: 状态文件不同步？

**A**: 确保所有写操作后调用 `complete`:
```bash
python -m orchestrator complete . <step_id>
```

### Q4: 如何调试Agent上下文注入问题？

**A**: 设置环境变量启用调试：
```bash
export ORCHESTRATOR_DEBUG_AGENT=1
python -m orchestrator start . <step_id> --inject-context
```

### Q5: 循环执行如何避免死循环？

**A**: 设置 `max_iterations` 和合理的退出条件：
```yaml
loop:
  max_iterations: 10
  condition: "has_failing_tests && iteration < 10"
```

## 总结

Orchestrator 通过以下机制实现工作流的强制执行：

1. **状态机** - 维护完整生命周期，阻止非法转换
2. **令牌系统** - 授权和权限控制，防止越权操作
3. **Agent调度** - 自动加载和注入规范，确保角色一致性
4. **验证引擎** - 自动产物验证，fail-fast机制
5. **门禁管理** - 产物化审批，下游强依赖
6. **事件溯源** - 自动记录执行历史，完整审计追踪

让AI工作流从"依赖自觉"升级为"协议强制"。
