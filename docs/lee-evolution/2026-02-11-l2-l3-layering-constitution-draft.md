# L1/L2/L3 分层宪法草案（Draft v1.1）

- 日期：2026-02-11
- 状态：Draft
- 主题：`L1 = 决策层`，`L2 = 多 agent 编排层`，`L3 = 单 agent 工作流`
- 本次更新：补充“责任闭环、授权拒绝、分层反模式、落地顺序”

## 一句话原则（可直接写入宪法）

> L3 是单-agent、可验证的工作单元；L2 是多-agent 的编排与协作层；L1 是人类主导的目标与边界决策层。  
> agent 只能在被授权层内行动，不得越权跨层执行。

## 1. 分层正式定义

### L1：决策层（Human-Led Governance）

定义：

> L1 负责业务目标、优先级、风险取舍与关键门禁决策。  
> L1 可以参考 AI 建议，但最终责任归人类决策者。

边界：

- 可做：定目标、定红线、批示推进/暂停/回滚。
- 不可做：把工程执行责任下放给“无边界 AI 自由发挥”。

### L2：多 agent 编排层（Multi-Agent Orchestration）

定义：

> L2 只做调度、依赖管理、门禁编排与失败处理；  
> L2 不直接产出工程交付物。

边界：

- 可做：编排 L3、设置 Human Gate、重试/回滚/分流。
- 不可做：直接改代码、直接写测试、替代 L3 完成交付。

### L3：单 agent 工作流（Single-Agent Workflow，允许并发）

定义：

> 一个 L3 workflow 由一个主责任 agent 完成，从入口到出口的关键决策归该 agent；  
> L3 可调用工具/脚本/runner，但禁止在内部发起新的长生命周期 agent 会话。

典型 L3：

- `L3-FE-DEV`：前端开发，输出前端 PR + 自测证据。
- `L3-BE-DEV`：后端开发，输出后端 PR + 自测证据。
- `L3-INTEGRATION-TEST`：联调测试，输出 E2E 报告 + 日志包。

并发语义：

- 多个 L3 实例可并发。
- 每个实例仍保持“单主责任 agent”。

## 2. 责任闭环（宪法核心增补）

### 2.1 失败归因矩阵

- `L3 失败 = 执行问题`：实现、验证、工件质量不达标。
- `L2 失败 = 编排问题`：依赖关系、时序、门禁、重试策略失效。
- `L1 失败 = 决策问题`：目标错误、风险取舍失当、门禁策略错误。

### 2.2 闭环处置规则

1. 先判层：任何失败先归到 L1/L2/L3 某一层。
2. 再整改：仅由该层责任人发起纠偏动作。
3. 留证据：所有整改必须回写到对应层的 Evidence。

## 3. 授权与拒绝机制（防“好心越权”）

### 3.1 层内授权原则

- AI agent 必须“层绑定”（Layer-Pinned），不能自行切换层级。
- 层级切换只能由 L2 编排动作或 L1 人类授权触发。

### 3.2 标准拒绝规则（必须可执行）

- 对 L3：收到“改需求/改优先级”请求时，必须拒绝并回传 L2/L1。
- 对 L2：收到“直接写代码/直接修 Bug”请求时，必须拒绝并派发 L3。
- 对 L1（AI 助手形态）：不得替代人类做最终风险拍板。

## 4. 防走样硬规则

### 规则 1：L3 内禁止横向 agent 调用

- 允许：工具、脚本、runner、测试框架。
- 禁止：L3 内再起长生命周期 agent 参与决策。
- 若需跨职能协作（如 FE+BE 对齐），必须上升到 L2 编排。

### 规则 2：L3 输入输出必须是无歧义工件

- 输入：Spec、代码、接口文档、测试用例等静态工件。
- 输出：PR/Patch、测试报告、日志包、截图证据等交付工件。
- 仅“建议”而无工件，不视为 L3 完成。

### 规则 3：L2 只编排，不干活

- L2 只负责：调度 L3、安排门禁、决策失败处理。
- L2 不负责：任何具体工程产出。

### 规则 4：越界即违规

> 任何 agent 跨越自己所在层去完成其他层的职责，视为违规。

## 5. 分层反模式清单（第一版）

### 5.1 L3 常见违规（执行层）

- 在 L3 内自行发起“临时 PM/QA agent”共同决策。
- 未完成可验收工件即宣告“任务完成”。
- 发现需求冲突时直接改需求而不回抛 L2/L1。
- 联调失败后修改编排逻辑而不经 L2。
- 证据缺失（无日志、无测试、无结果快照）。

### 5.2 L2 膨胀信号（编排层）

- 编排 agent 直接提交代码或测试脚本。
- 出现“超级工作流”把 FE/BE/QA 混在同一决策上下文。
- 失败处理仅靠追加提示词，没有结构化回滚/重试策略。
- 把验收判断建立在长对话而非 Verifier 结果上。

### 5.3 L1 风险征兆（决策层）

- 人类把关键风险拍板默许给 AI 自动决定。
- 目标未冻结就持续推动 L2/L3 执行。
- 缺少显式 Gate（需求确认、架构批准、上线批准）。
- 不要求责任归因，导致“所有人都像对的”。

## 6. 与 Verifier / Evidence 的对齐要求

- 每个 L3 必须绑定：`1 主责任 agent + 1 组 Verifier + 1 份 Evidence Bundle`。
- L2 只消费 Verifier 结论，不以“对话长度/语气”作为验收依据。
- L1 的 Gate 决策必须引用 L2 汇总证据，不接受无证据拍板。

## 7. 落地模板与执行顺序

### 7.1 建议模板：`L2-FEATURE-DELIVERY`

1. `L3-SPEC`（可选）
2. `L3-FE-DEV` 与 `L3-BE-DEV`（可并发）
3. `L3-INTEGRATION-TEST`
4. Human Gate：需求确认 / 架构批准 / 上线批准

### 7.2 推荐后续落地顺序

1. 先补齐各层“反模式清单”并接入运行时校验。
2. 选一个真实功能做完整 L1/L2/L3 映射演练。
3. 固化 `L3 Evidence / Verifier` 规范。
4. 固化 `L2 失败回路`（重试、降级、回滚、人工接管）。
