## 高优先级缺陷

### P1-01: 工具调用守卫未实现

**状态**: 🔴 未实现 (理论设计阶段)

**问题描述**:
- TokenManager 和 ToolGuard 已实现，但缺少实际的工具拦截器
- AI工具（Claude Code等）调用 Write/Edit/Bash 时，**无法强制验证令牌**
- 导致：令牌系统只是"建议"，LLM可以绕过

**影响**:
- 核心安全机制失效
- 无法真正实现"强制执行"
- 依赖AI平台的Hooks支持（Claude Code目前不支持）

**根因**:
```
AI工具调用流程:
  LLM决定调用Write工具
    ↓
  [缺失] 工具拦截器 - 验证 WORKFLOW_TOKEN
    ↓
  直接执行Write (无守卫)
```

**建议修复**:
1. **短期**: 在CLAUDE.md中强化提示词约束
2. **中期**: 与Claude Code团队沟通，请求Pre-Tool-Use Hook支持
3. **长期**: 开发独立的工具代理层 (Tool Proxy)

**相关代码**:
- `orchestrator/core/token_manager.py:ToolGuard` (已实现但未使用)
- `INTEGRATION.md` 第96-112行 (Hooks设计)

### P1-02: Validator引擎未实现

**状态**: 🔴 未实现 (目录存在但为空)

**问题描述**:
- `orchestrator/validators/` 目录存在但所有文件为空
- `workflow.yaml` 中可以定义 validators，但执行时不会实际验证
- `orchestrator validate` 命令存在但无实际验证逻辑

**影响**:
- 产物质量无法自动验证
- 依赖人工检查，容易遗漏
- workflow.yaml 中的 validators 配置无效

**建议修复**:
```python
# validators/schema_validator.py
import jsonschema

class SchemaValidator:
    def validate(self, data: Any, config: Dict) -> ValidationResult:
        schema_path = config.get("schema_path")
        schema = load_json_schema(schema_path)
        try:
            jsonschema.validate(data, schema)
            return ValidationResult(passed=True)
        except jsonschema.ValidationError as e:
            return ValidationResult(passed=False, error=str(e))

# validators/file_validator.py
class FileValidator:
    def validate(self, data: Any, config: Dict) -> ValidationResult:
        files = config.get("files", [])
        missing = [f for f in files if not Path(f).exists()]
        if missing:
            return ValidationResult(passed=False, error=f"Missing: {missing}")
        return ValidationResult(passed=True)
```

def approve_gate(self, gate_id: str, approver: str):
    # ... 现有逻辑 ...

    # 新增: 解锁依赖此gate的步骤
    for step_id, step_data in self._state["steps"].items():

### P2-01: Agent规范缓存未实现

**状态**: 🔴 未实现

**问题描述**:
- `AgentLoader` 每次加载都从文件系统读取
- 对于相同的 agent_id，重复解析 YAML
- 性能影响：每步骤启动增加 50-100ms

**建议修复**:
```python
class AgentLoader:
    _cache: Dict[str, AgentSpec] = {}  # 内存缓存

    def load(self, agent_ref: str) -> AgentSpec:
        if agent_ref in self._cache:
            return self._cache[agent_ref]

        spec = self._load_from_file(agent_ref)
        self._cache[agent_ref] = spec
        return spec

    def invalidate_cache(self, agent_ref: str = None):
        # 支持手动清除缓存
        if agent_ref:
            self._cache.pop(agent_ref, None)
        else:
            self._cache.clear()
```

def execute_step_with_retry(step_id: str, max_retries: int = 3):
    for attempt in range(max_retries):
        try:
            result = execute_step(step_id)
            if result.success:
                return result
        except Exception as e:
            if attempt == max_retries - 1:
                raise
            delay = 2 ** attempt  # 指数退避

## 架构层面问题

### A-01: 状态存储使用文件系统，缺少事务性

**问题描述**:
- `state.yaml` 使用 `write_text()` 覆盖写入
- 并发写入可能导致数据损坏
- 无原子性保证

**影响**:
- 在多进程环境下不安全
- 状态文件可能损坏

**建议方案**:
1. **短期**: 使用文件锁 (`fcntl.flock`)
2. **中期**: 写入临时文件 + 原子重命名
3. **长期**: 迁移到 SQLite (保持文件系统优势)

```python
import fcntl

def save_state_atomic(state: Dict, path: Path):
    # 写入临时文件
    temp_path = path.with_suffix(".tmp")
    temp_path.write_text(yaml.dump(state))

    # 原子重命名
    temp_path.replace(path)
```

### A-02: 事件溯源和CQRS未完全实现

**问题描述**:
- EventLog 记录了事件，但状态机仍是直接修改状态
- 无法从事件日志重建状态（Event Sourcing）
- 无法实现时间旅行调试

**建议方案**:
实现真正的Event Sourcing：
```python
class EventSourcedStateMachine:
    def __init__(self, project_dir: str):
        self.events = EventLog(project_dir).load_all()
        self.state = self._rebuild_from_events(self.events)

    def _rebuild_from_events(self, events: List[Event]) -> Dict:
        state = {}
        for event in events:
            state = self._apply_event(state, event)
        return state
```

## 贡献指南

### 如何报告缺陷

1. 在项目 Issue Tracker 创建新Issue
2. 使用模板：Bug Report
3. 提供：
   - 复现步骤
   - 预期行为 vs 实际行为
   - 版本信息
   - 相关日志

### 如何提交改进建议

1. 创建 Issue，使用模板：Feature Request
2. 或编写 RFC 文档放在 `docs/`
3. 参与讨论和评审

### 开发流程

1. Fork 项目
2. 创建功能分支 (`feature/P1-02-validator-engine`)
3. 编写代码和测试
4. 提交 Pull Request
5. 等待Review

## 总结

### 当前最紧迫的问题

1. **工具调用守卫未实现** (P1-01) - 核心安全机制缺失
2. **Validator引擎未实现** (P1-02) - 产物质量无法保证
3. **Gate审批不完整** (P1-03) - 门禁可以被绕过

### 架构改进方向

1. **从"建议"到"强制"** - 实现真正的工具拦截
2. **从"单机"到"分布式"** - 支持远程执行
3. **从"状态机"到"事件溯源"** - 完整的可审计性

### 长期愿景

打造一个：
- ✅ **真正强制执行** 的AI工作流引擎
- ✅ **跨平台** 的LLM集成方案
- ✅ **企业级** 的可靠性和可审计性
- ✅ **开放扩展** 的插件生态
